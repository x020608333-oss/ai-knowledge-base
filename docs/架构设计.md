# 架构设计详解

## 1. 整体架构（RAG）

本项目是一个典型的 **RAG（Retrieval-Augmented Generation，检索增强生成）** 系统，分为两条主链路：

### 写入链路（知识入库）
```
上传文件 → 异步解析(Tika/PDF Reader) → 分块(TokenTextSplitter) → 向量化(EmbeddingModel) → 写入向量库(SimpleVectorStore)
```
同时把文档元信息（文件名、状态、分块数）写入数据库（默认 H2，生产可切换 MySQL），用于状态追踪与来源展示。

### 读取链路（问答）
```
用户提问 → 加载会话历史记忆 → 向量检索 Top-K → 阈值过滤 → 组装 Prompt(系统提示+上下文+历史) → LLM 流式生成 → 持久化+缓存 → SSE 输出(正文+引用来源)
```

## 2. 关键设计决策

### 2.1 为什么用 RAG 而不是微调（Fine-tuning）？
- 微调适合"改变模型的表达风格/领域语气"，不适合"注入事实性知识"。
- RAG 可**动态更新**知识（改文档即可），**可溯源**（给出引用），**成本低**（无需训练），且能有效**抑制幻觉**。
- 二者常配合使用，本项目聚焦 RAG。

### 2.2 分块（Chunking）策略
- 使用 `TokenTextSplitter` 按 token 数切分，并保留一定重叠（overlap），避免语义在边界被截断。
- 分块过大 → 检索不精准、占用上下文窗口；过小 → 语义不完整、召回噪声多。需要在"召回率"与"精度"间权衡。

### 2.3 相似度阈值过滤
- 检索后按 `similarityThreshold` 过滤低相关片段，避免把无关内容塞进上下文，反而"带偏"模型。
- 若检索结果为空，Prompt 中明确告知模型"无参考资料"，模型据此回答"无法找到相关信息"，而非编造。

### 2.4 提示工程（Prompt Engineering）
- 系统提示中**强约束**模型"只能基于参考资料回答 + 标注引用编号"，是抑制幻觉的关键工程手段。
- 低温度（temperature=0.3）提升答案稳定性与确定性。

### 2.5 流式输出（SSE）
- 采用 `Flux<ServerSentEvent<String>>` 返回 `text/event-stream`，实现打字机效果，降低首字延迟（TTFT），提升体验。
- 生成过程放在独立线程池 `Schedulers.fromExecutor(ragTaskExecutor)` 上，避免阻塞。

### 2.6 异步文档处理
- 上传接口**立即返回**，解析/向量化交由 `@Async` 线程池后台执行，状态机（PENDING→PROCESSING→COMPLETED/FAILED）追踪进度。
- 拒绝策略用 `CallerRunsPolicy` 做背压兜底，防止 OOM。

### 2.7 多轮记忆与会话
- 会话与消息落库（默认 H2，生产可切换 MySQL），`findRecentMessages` 取最近 N 条构建上下文，实现"带记忆的追问"。
- 可演进为"问题改写（Query Rewrite）"解决指代消解；历史记忆亦可切换到 Redis 等外部存储。

### 2.8 缓存
- 当前实现：对热点问题答案做 **Caffeine 本地缓存**（TTL 1h、容量上限 1000），通过 Spring 缓存抽象 `CacheManager` 与业务层解耦。
- 进阶方向：切换 **Redis 分布式缓存**，或做**语义缓存**（对问题向量化后按相似度命中），可大幅降低重复问题的 LLM 成本与延迟。

## 3. 可扩展方向（体现深度）
- **混合检索（Hybrid Search）**：向量检索 + 关键词/BM25，再用 Rerank 模型重排序，提升召回质量。
- **多知识库 / 多租户**：元数据过滤（metadata filter）隔离不同用户的文档。
- **重排序（Rerank）**：引入 Cross-Encoder 对初排结果精排。
- **Agent / 工具调用**：从"问答"升级为"能调用工具（查库、搜索、计算）的智能体"。
- **可观测性**：接入 Langfuse 等对每次 LLM 调用做追踪、评估（延迟/成本/命中率）。
